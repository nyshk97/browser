# ページの `gg` / `G` で最上部・最下部へスクロール

## 概要・やりたいこと

ページにフォーカスがある状態で、vim と同じキーで縦方向の端へ飛べるようにする。

| 操作 | 動作 |
|---|---|
| `g` `g`（1 秒以内の 2 連打） | スクロール対象を最上部へ |
| `G`（Shift+g） | スクロール対象を最下部へ |

長い記事・GitHub の diff・Slack のログを読んでいるときに、ホイールを何度も回さずに端へ戻れるようにするのが目的。

**`j` / `k` / `Ctrl-d` へは広げない**（今回きり）。`feedVimKey` の戻り値は `'top' | 'bottom' | null` の
2 値に固定し、ファイル名・スイート名も `vim-scroll` のままにする。
j/k は GitHub の issue リストや Gmail の j/k（選択移動）と**二重発火するサイトが実在する**ため、
`preventDefault` しない方針と相性が悪い。その設計が未決のまま抽象だけ先行しても役に立たない。
後から足すときは呼び出し元が 1 か所しかないので、戻り値の型を広げる小さい変更で済む。

## 前提・わかっていること

### 既存の実装パターン

このリポジトリには「ページ側でキー・入力を扱う」経路が 2 つある。

1. **main の `before-input-event`**（`src/main/registry.ts:788`）— Peek の Esc を拾っている
2. **隔離ワールドへの注入**（`src/shared/swipe-gesture.js` + `attachSwipeNavigation`、`src/main/registry.ts:952` 付近）— トラックパッドのスワイプで戻る / 進む

**今回は 2 を採る。** `before-input-event` には `input.key` しか渡ってこないため、
**ページの入力欄にフォーカスがあるかどうかを main 側から判別できない**。
検索ボックスに `G` と打った瞬間に最下部へ飛ぶことになり、日常的に踏む。
注入方式ならページ内で `document.activeElement` と `isComposing` を見て除外できる。

swipe が既に「`dom-ready` / `did-navigate` ごとの再注入」「二重登録の抑止マーカー」を
解決済みなので、その型をそのまま踏襲する。

### 仕様（`/dig` で確定した決定事項）

- **スクロール対象の決め方**: `document.activeElement` の祖先を辿って縦スクロール可能な要素を探し、
  見つからなければ画面中央（`elementFromPoint(innerWidth/2, innerHeight/2)`）の要素から同じことをし、
  それも無ければ `document.scrollingElement`。
  普通の記事ページはルートに当たり、Gmail / Slack / Notion のように**ルートが動かず内側の div が
  スクローラ**になっているサイトでも効く。
  登り方は swipe の `hasScrollRoom`（`src/shared/swipe-gesture.js:151`）と同じ考え方
  （あちらの横方向を縦にしたもの）。ただし**祖先探索は `overflowY` が `auto`/`scroll` の要素だけを
  見て、`document.body` と `document.documentElement` は採らずに候補 3 へ譲る**。
  - `hasScrollRoom` が持つ `node === document.scrollingElement` の特例は持ち込まない。
    持ち込むと、`html` に数 px の余りがあるページで**ルートが先に採られて内側スクローラまで
    辿り着かず**、`gg` / `G` が数 px 動いて終わる。
  - 逆に `body` を素通しにすると、**`body { overflow-y: scroll }`（スクロールバー常時表示のために
    よく使われる）のページで完全に無反応になる**。`body` は条件に合致するが、overflow の viewport
    伝播で実際に動くのは `scrollingElement` 側なので `body.scrollTo()` は何もしない。しかも
    何もフォーカスしていない初期状態では `activeElement` が `body` そのものなので、必ずここに落ちる。
  - 通常ページは最後の候補（`scrollingElement`）で確実に拾えるので、これで両方塞がる。
- **なめらかにスクロール**（`behavior: 'smooth'`）。ただし `prefers-reduced-motion: reduce` が
  有効なら即時（`'auto'`）に落とす。
  **smooth 固定のまま作る。** 長大なページで待たされるかは実サイトの手触り次第なので、
  人間の動作確認（後述）で NG なら**そのときに倒す**。倒すと `behavior` だけでなく
  **Phase 3 の到達 polling・アサーションの書き方・`VERIFY.md` の記述がまとめて変わる**ので、
  倒した場合は「ログ > 方針変更」に記録したうえで仕様セクションのこの行も書き換える。
- **`G` は押した時点の `scrollHeight` まで飛んで終わり**。無限スクロールページ（X・Facebook 等）で
  到達後にページが伸びても追従しない（追従させると SNS で無限に落ち続ける）。
- **`gg` の 1 打目と 2 打目の猶予は 1000ms**。超えたら 1 打目に戻す
  （猶予なしにすると、`g` を押して放置した後の `g` で誤爆する）。
- **`preventDefault` しない**。GitHub の `g c`・Gmail の `g i` のような `g` プレフィックスの
  ショートカットを潰さない。`gg` や `G` 単体を割り当てているサイトはほぼ無いので、
  最悪でも「スクロールもする」で済む。食い切ると `g` プレフィックスが全滅する。
- **効かない条件**:
  - 入力欄にフォーカスがある（`input` / `textarea` / `select` / `contenteditable` / `[role="textbox"]`）
  - IME 変換中（`event.isComposing`）
  - 修飾キーが付いている（`metaKey` / `ctrlKey` / `altKey`）
  - iframe にフォーカスがある（**メインフレームにしか注入しない**）
- **iframe には注入しない**。swipe が全フレームに入れているのは「ホイールが iframe の境界を
  越えて親へ伝わらない」ためだが、**キーはフォーカスに付いて回る**ので、iframe をクリックして
  いない限りメインフレームで受けられる。広告・トラッキング iframe にまで入れずに済む。
  副作用として、YouTube 埋め込み等をクリックした後は効かなくなる（ページの余白をクリックすれば戻る）。
- **設定項目は足さない**。swipe と同じく常に ON。`preventDefault` せず入力欄も除外するので、
  切りたくなる場面が想定しにくい。

### 検証まわりで分かっていること

- `scripts/verify-switcher.mjs:99` が CDP の `Input.dispatchKeyEvent` を使っている。
  **同じ方法で実アプリのページに `g` / `G` を撃ち、`scrollTop` を見る自走検証が組める。**
- **CDP の合成キーは撃った先へフォーカスが移る**（`scripts/verify-switcher.mjs:276` に実測が残っている。
  一度ページへ撃つと以降オーバーレイへ撃っても届かない）。**タブのページへ大量に撃つスイートなので、
  後続スイートのキー検証を巻き込んで壊す**。実行順の位置に注意が要る。
- **`Input.dispatchKeyEvent` は `text` を渡さないと文字を挿入しない。** リポジトリの先行例
  （`scripts/verify-switcher.mjs:108` / `scripts/verify-live-folder.mjs:670`）はどれもショートカット用で
  `text` を渡していないので、そのまま踏襲すると「入力欄に文字が入る」の検査が空振りする。
- ページ target は **URL 完全一致で 1 件に絞る**（`scripts/verify-switcher.mjs:63`。ブラウザ UI 自身が
  `nemo://ui/index.html` なので部分一致だと UI を掴む）。ほかの検証が残したウィンドウと衝突するので、
  URL に `?w=<windowId>` を付けて自分のページを一意にする。
- `scripts/verify-all.mjs` はスイートを `want('<名前>')` で分岐して呼ぶ形
  （`switcher` は `scripts/verify-all.mjs:267` と `:330`）。
- `scripts/lib/verify-targets.mjs` に「変更ファイル → 回す検証」の逆引きがあり、
  `KNOWN_TARGETS` / `NEEDS_APP` / `OWNERS` の 3 か所を触る必要がある。
  対応表の実在チェックは `scripts/verify-targets.test.mjs` が固定しているので、
  **足し忘れるとユニットテストが落ちて気づける**。
  なお `src/main/registry.ts` は意図的に `OWNERS` 外（`scripts/lib/verify-targets.mjs:88`）で、
  **触るとフルに倒れる**。
- `test-pages/` に検証用の静的ページ置き場がある（`scripts/test-server.mjs` が配る）。
- 回すかどうかは `scripts/verify-all.mjs:101` の `want = (name) => only.size === 0 || only.has(name)`
  ただ 1 つで決まる。**`--changed` は選んだ名前を `only` に足してから `want` を通る**ので、
  「既定では回さないが `--only` / `--changed` では回る」は `only.size === 0` の側に
  opt-in 集合を噛ませるだけで作れる。

### 決めたこと: このスイートはフル既定から外す

直前のコミットでフルを 529s → 372s に縮めたばかりなので、**`pnpm verify` の既定には入れない**。
`--only vim-scroll` と `--changed`（`src/shared/vim-scroll.js` 等を触ったとき）でだけ回る。

代償として、**CDP の合成キーが後続スイートを壊す回帰を CI で拾えなくなる**。
実行順の最後（`http-auth` の後・`restart` の前）に置いたので後続は `restart` だけだが、
Phase 4 で**一度だけ既定除外を外してフルを通し**、`restart` が無傷であることを確認する。

### 注意点

- **smooth なので、キーを撃った直後に `scrollTop` を読むと 0 のままで偽 FAIL になる。**
  到達するまで polling する（タイムアウト付き）。`networkidle` 直後にスクショを撮って
  「読み込み中...」を掴むのと同じ型の罠。
- **「効かないこと」の検証は、効く経路が動いていることとセットで撃つ。**
  入力欄で `G` を打って動かないことだけを見ても、そもそも機能が死んでいる場合と区別が付かない。
- `did-navigate` だけでなく `dom-ready` にも張る。**bfcache から復元されると `dom-ready` は
  出ない**ので、片方だけだと「一度戻った後は効かない」になる（swipe が実際に踏んでいる）。

## ログ

### 試したこと・わかったこと

- **`connectPage` は読み込み完了を待たないと落ちる。** target は URL で見つかるのに
  document がまだ無く、`document.scrollingElement` が null で最初の実行が例外になった。
  `document.readyState === 'complete'` まで待つようにした（中身を JS で組み立てる fixture なので
  `interactive` では足りない）。
- **入力欄を文書の流れの中に置くと「入力欄では飛ばない」の検査が必ず落ちる。**
  スクロール位置が下のときに文字を打つと、Chromium が**キャレットを見せるためにスクロールする**
  （実測 `scrollTop 7013 → 173`）。gg / G とは無関係の交絡なので、fixture の入力欄を
  `position: fixed` にして常に画面内に置いた。
  `input.value` は `"G"` になっていたので `preventDefault` していないことは同時に確認できている。
- **修正前 FAIL の確認**: `attachVimScroll` の呼び出しを落として `--only vim-scroll` を回すと、
  ケース 1・2・4 が FAIL する（`gg で最上部へ戻る — scrollTop 13986 → 13986`、
  `内側スクローラ — scroller 0 → 0 / max 13812`）。
  ケース 3・5 は「動かないこと」を見るので**注入が無くても PASS する**（構造上そうなる）。
  これが計画で「効く経路とセットで撃つ」と決めた理由そのもの。
- **フルへの増分は約 10s**（vim-scroll あり 6:42 / なし 6:32）。決めた上限 30s の内側なので
  固定待ちは削っていない。
- **隔離ワールド ID は 1731。** 1730 は会議のプローブ（`call-coordinator.ts:CALL_WORLD_ID`）が
  既に使っていた（計画では「swipe と別」しか決めていなかったので 1730 を採ってしまった）。
- **shadow DOM の入力欄・内側スクローラは、素直に書くと両方とも取りこぼす。**
  `document.activeElement` も `event.target` も**ホスト要素に retarget される**ので
  `deepActiveElement()` で内側へ辿り、逆に祖先探索は `parentElement` が shadow 境界で
  `null` になるので `getRootNode().host` へ跨ぐ。両方入れて初めて Web Components のアプリで効く。
  **自走検証の fixture には shadow DOM が無いので、ここの回帰網は無い**（下の「残っている宿題」）。
- **フル 1 回目に `FAIL あり` で終わったが再現しなかった。** 出力を保存しておらず、
  どのスイートかを特定できていない。同じ条件のフルを 2 回（vim-scroll 込み / 既定）回して
  どちらも全 PASS。vim-scroll 自身と後続の `restart` は 2 回とも PASS しているので、
  **切り分けは付いていない**（既存スイートの flake の可能性が残る）。

### 残っている宿題

- **shadow DOM のケースが自走検証に入っていない。** `test-pages/scroll-*.html` は素の DOM だけなので、
  `deepActiveElement` と shadow 境界跨ぎが壊れても `verify-vim-scroll` は通ってしまう。
  確認は使い捨てプロファイルの素の Electron で一度やった（境界跨ぎを外すと FAIL することも見た）が、
  **その場限りで残っていない**。fixture を 1 枚足すのが筋。
- **`event.repeat`（押しっぱなしのオートリピートを `gg` にしない）が検証できていない。**
  Electron の `sendInputEvent` は `isAutoRepeat` を `KeyboardEvent.repeat` にマップしない
  （true/false とも `repeat=false` を実測）。CDP の `Input.dispatchKeyEvent` には `autoRepeat` が
  あるので、`verify-vim-scroll.mjs` 側なら撃てる可能性がある。
- **⌘G（修飾キー付き）で飛ばないことの検査が無い。** 実装は早期 return しているが網が無い。
